# Production readiness audit: Ringee n8n integration

**Date:** 2026-11-24. **Scope:** `n8n-nodes-ringee` (this repository) and the additive public-API changes in `ringee-app`. Nothing was committed, pushed, published or deployed; every change is uncommitted in both repositories.

## CPS protection update — 2026-11-24

**Current recommendation: NO-GO for a global Telnyx CPS protection launch.** This supersedes the earlier conditional recommendation below. Local n8n validation passes; production enforcement has not been deployed or verified.

The current Ringee implementation adds an account-scoped distributed pacing gate at HTTP egress, a PostgreSQL queue, cancellable operations, bounded expiry and retries, workspace AI concurrency admission (default 25), and atomic credit admission holds. Queue-enabled Start Call returns 202 queued promptly. Older or queue-disabled servers can still return 201 initiating. Replays and reads preserve queue deadlines. The node supports both responses and does not wait for dispatch.

RA-06 is now partly addressed in code: shared AI concurrency and dispatch-time credit reservations replace the previous unlimited admission. The default USD 0.10 reservation is an admission estimate, split across the two existing settlement keys; it is not a maximum call-cost guarantee. Existing browser/SIP paths and full reservation coverage remain release conditions.

Release blockers: direct browser/SIP/PBX traffic is outside the HTTP egress gate; the actual Telnyx billing identity and shared coordination across staging/production are unverified; migrations are prepared for manual application only; no live n8n worker/restart test or provider-CDR/invoice reconciliation has been performed. Existing call triggers do not announce operations that never dial: use bounded status polling for cancelled, expired or pre-dispatch failed operations.

CodeRabbit first pass reviewed all tracked and new implementation files in both repositories. Its persistent-idempotency-key documentation finding was confirmed and corrected. The incidental pnpm lock/workspace files created during validation were removed; npm and its existing package-lock.json remain authoritative. The second review found four documentation issues (capacity retry policy, event ID correlation, acceptance wording and older-server compatibility), all independently confirmed and corrected. Verification also closed unkeyed manual Start Call admission; new regression tests cover the refusal and explicit-key retry. The final review and validation are recorded in the Ringee CPS report.

See Ringee's docs/telnyx-cps-cost-protection.md and docs/financial-protection.md for enforcement coverage, operator controls, test evidence and release gates. Nothing was committed, pushed, deployed, published, charged, or changed in Telnyx.

Local CPS validation: `npm run validate` passes lint, types, all 444 tests, build and package checks; formatting passes separately. This includes queued deadlines, 1,000 mock API requests, stable record keys, manual execution without a stable key, and explicit-key replay. Backend tests separately exercise the actual PostgreSQL queue and Redis clocks; the mock node test does not prove n8n worker persistence.

The third CodeRabbit review corrected the main event/status workflow, post-deadline branching and old-server guidance. Its inline `dispatch_deferred` idempotency question was verified in Ringee: the same key now retries only a denial proven before HTTP; uncertain provider responses retain their binding. Separate database-pressure tests cover a committed queue operation whose acknowledgement is lost.

The fourth review asked whether status reads expire overdue operations and corrected an unconditional replay promise after timeouts. Ringee status reads do expire operations atomically. Independent verification also fixed a concurrent-read snapshot race: all 20 concurrent owner polls now return the expired state, while a different workspace cannot expire it. Timeout guidance now handles both a new acceptance and an idempotent replay under the same key. The final post-fix CLI review is captured in the Ringee CPS report.

The fifth review confirmed missing eventless-operation handling in example templates. All eight direct Start Call templates now retain operation identity/deadline and perform one bounded status check independently of events, including an unresolved/error output. The watcher never retries a call or creates duplicate CRM results; template 02 labels accepted queued calls accurately. Revised templates are explicitly marked not reimported or validated in a live n8n worker; users must connect attention output to their own idempotent follow-up. New structural/expression regressions verify batch deadlines, terminal statuses and absence of paid retries.

The sixth (final) review raised four template questions. Each was checked against n8n's engine source and Ringee's API instead of assumed. **A failing step beside the watcher stops it: confirmed** against n8n-core 2.49. Branches under one node run one at a time, topmost first, and an unhandled node error abandons every branch still waiting. The API itself answers a read of a queued call with `200 queued`, so that read does not fail by design; but the result read in template 00, the sheet update in 02 and the log write in 06 could fail for any other reason (a `5xx`, a revoked key) and silently removed the status check. They now continue on an error output into a named node, the watcher stays the last branch (so its Wait delays nothing), and a test replays n8n's run order for every template. **Dropped `expires_at`: refuted.** The cited revision is the committed scaffold; the working handler returns the deadline on start, replay and reads, and new tests push a ten-minute queued answer through all eight templates' own expressions (a 601-second wait). **Retry after expiry reaching the unconnected branch: refuted.** Ringee reads the call as it is now and answers a same-key repeat of an expired, cancelled or pre-dispatch-failed call with `409` and a code and no status body, so it arrives on Start Call's error output (or stops the run) and never reaches the selector; the contract is documented as a table and pinned by a test over every template's selector. What stays open: the templates have still not run on a real n8n worker. The run order they now rely on was read from n8n-core 2.49's source and is replicated in the tests, not observed.

## Earlier public API audit (historical baseline)

## Executive summary

**Recommendation: CONDITIONAL GO. Do not publish today.** The code, templates and docs are in good shape and every confirmed P0 and P1 defect that could be fixed without a product decision is fixed and covered by a test. Three conditions are still open:

1. **No real n8n run.** The end-to-end test with a real n8n server and the real backend booted over HTTP was not done: the disk was full, so n8n could not be installed (about 3 GB needed). The acceptance criteria require templates 00, 01 and 02 to pass this on staging before release.
2. **RA-06, a decision (P1):** nothing limits how many AI calls one workspace can have live at once, and the only balance gate is `balance > 0` (see below). An n8n loop makes this easy to hit. The owner must accept the risk or choose a cap before publication.
3. **Release order:** the backend change must be deployed and verified before the node is published. The node now refuses to place calls against a backend that does not confirm idempotent starts, so a mistake in the order fails safe, but the node would be useless.

What was found and fixed in this audit (details below): a retried Start Call could be answered as a success when no call had been placed (P1); two templates started paid calls from unauthenticated webhooks (P0); four templates wrote results before the AI analysis existed or labelled them wrongly (P1); a template overwrote one shared HubSpot contact (P1); the contact upsert created duplicates under concurrency (P2); pagination returned repeated and missing rows (P2); the AI-tool path could place the same call twice (P1/P2). No cross-organization access was found.

## Limitations and untested scenarios

- Real n8n end to end (any template), including restart and worker scenarios; the backend booted over HTTP with a mocked Telnyx and real webhook delivery into a Ringee Trigger; recordings and transcripts over the real API.
- The AI Agent tool with a real model (prompt injection, tool-call loops). The tool's duplicate-call and iteration limits are covered by unit tests and the `maxIterations` setting only.
- Live Google, HubSpot, Slack, Facebook Lead Ads and GoHighLevel: none of the templates was live-tested.
- Multi-process backends beyond the shared database and Redis (the guarantees are enforced by the unique index and Lua script, which the tests exercise on real services).
- The "Output" option and Contact "Simplify" for AI tools were not added. They are a UX and context-size improvement, not a verification blocker; the Transcript tool still returns the whole transcript to the model, so keep it out of agents that read untrusted text.

## Rollback plan

- **Backend defect:** roll the ECS service back to the previous task definition. There is no schema change to undo. The capabilities route disappears (`404`), so the node refuses to place calls (it fails safe, no duplicates); contacts and calls routes answer `404`; existing calls and contacts stay valid.
- **Node defect:** `npm deprecate` the bad version and publish a patch. Installed copies keep running until updated; templates can be switched off by deactivating the workflows.
- **Webhook failures:** failed deliveries are listed per integration; there is no replay API, so recover with a workflow that lists calls since a date (`Call → Get Many`) and processes the missed ones.
- **Compatibility:** the node needs `GET /api/v1/capabilities` with `idempotentCalls: true`. A rollback of the backend to a version without it stops Start Call in n8n rather than risking duplicate calls. n8n 2.x (the current stable, 2.49.5, requires Node 24 or newer; the package itself declares Node 20.19 or newer).
